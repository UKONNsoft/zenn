## そもそも何のための記事か

Claude Code を入れて、`.claude/` というフォルダに設定を置けることまでは分かった。フックもスキルもサブエージェントも MCP サーバーも、そういう仕組みがあるらしいことは分かった。

**それで、自分のプロジェクトには結局どれを入れればいいのか。**

ここで止まる人がとても多いはずです。理由ははっきりしていて、**答えが人によって違うから**です。React でフロントエンドを書いている人に必要なものと、Python でデータ処理を書いている人に必要なものは違います。テストがあるプロジェクトと無いプロジェクトでも違います。だから解説記事はどうしても「こういう場合はこう」という一般論になり、読んだ人は自分がどの場合に当たるのか分からないまま終わります。

この「自分の場合はどれか」を、**Anthropic 公式のプラグインがプロジェクトを読んで判定してくれます**。名前は `claude-code-setup` です。

この記事では、まず**新しいプロジェクトを立ち上げるときの使い方**を、実際に動かした画面つきで最初から最後まで通します。そのあとで、**すでに動いているプロジェクトの点検に使う方法**を足します。後半では、このプラグインの正体と限界（そして X でよく見かける誤解）まで踏み込みます。

## 先に結論

3行で言うと、次のようになります。

1. `claude-code-setup` は実在する Anthropic 公式のプラグインで、インストールはコマンド1行です。
2. **設定はしてくれません。** 「何を設定すべきか」を診断して報告するだけで、ファイルは一切書き換えません。ここは誤解が広まっています。
3. **空のフォルダで走らせても何も出ません。** 判定材料がゼロだからです。先に最小の中身を作ってから走らせる、という順序が要ります。ただし材料は `package.json` である必要はなく、**説明を書いたテキスト1枚でも通ります**（開発プロジェクトでなくても使えますが、効き目は条件によります）。

### 空フォルダに何を入れる？

空っぽのフォルダでは空振りに終わるので、これから進めるプロジェクトの**「とりあえずのファイル」**が必要になります。具体的には、次のようなものです。

**① `package.json` — いちばん具体的に効く**
たとえばプロジェクトが Next.js など Node 関連だとしたら、このファイルが一番効果的に効きます。使う言語とライブラリが1ファイルで伝わるので、「Supabase を使うなら Supabase MCP」のように**名指しの推薦**が返ってきます。Python なら `pyproject.toml`、Rust なら `Cargo.toml`、Go なら `go.mod` が同じ役割を果たします。

> ※ `package.json` は npm（Node.js のパッケージ管理）のプロジェクト定義ファイルです。

この程度の短いもので構いません。完成させる必要はなく、**使う予定のライブラリが書いてあれば十分**です。

```json
{
  "name": "my-first-app",
  "dependencies": {
    "next": "^15.0.0",
    "react": "^19.0.0",
    "@supabase/supabase-js": "^2.45.0"
  }
}
```

**② コードファイル数個**
プロジェクトのマニフェストファイルが無くても構いません。単にソースコードファイルだけでも、その拡張子や import 文、コード内容から言語とフレームワークを推定してくれてアドバイスをくれます。`src/` や `tests/` といったフォルダの分け方も判定材料になります。

**③ 非プログラミングプロジェクトの説明テキスト1枚 — 通りますが、効き目は薄いです**
プロジェクトはプログラミング関連でなくてもよく、そのフォルダで何をしたいかを説明した `README.md` 1つでも**診断そのものは通ります**（「いま何に困っているか」まで書いてあること）。ただし**コードも `.claude/` の設定も無い文書だけのフォルダでは、推薦が一般論に寄ります**。この場合はプラグインを呼ばず、Claude へ普通に相談したほうが具体的な答えが返ります。比較検証は Step 3 に載せました。

# 第1部：新しいプロジェクトに導入する

## Step 1：プラグインを入れる

Claude Code を起動して、プロンプト（チャット欄）に次の1行を打ちます。

```
/plugin install claude-code-setup@claude-plugins-official
```

`@` の後ろの `claude-plugins-official` は**マーケットプレイスの名前**です。マーケットプレイスというのは、プラグインが並んでいる置き場のことだと思ってください。この公式マーケットプレイスは、**Claude Code を初めて対話モードで起動したときに自動で登録されます**。したがって、普通に使っている人は事前登録の作業をしなくてよく、上の1行だけで入ります。

:::message
CI やスクリプトなど、対話モードを一度も通らない環境では自動登録が走りません。その場合だけ、先に `claude plugin marketplace add anthropics/claude-plugins-official`（実行場所＝ターミナル）で登録しておく必要があります。
:::

ターミナルから入れることもできます。こちらは Claude Code を起動せずに実行できます。

```bash
# 実行場所＝ターミナル
claude plugin install claude-code-setup@claude-plugins-official
```

入ったかどうかは、次のコマンドで中身ごと確認できます。

```bash
# 実行場所＝ターミナル
claude plugin details claude-code-setup
```

実際の出力がこれです。

```
claude-code-setup 1.0.0
  Description: Analyze codebases and recommend tailored Claude Code automations
               such as hooks, skills, MCP servers, and subagents.
  Source: claude-code-setup@claude-plugins-official

Component inventory
  Skills (1)  claude-automation-recommender
  Agents (0)
  Hooks (0)
  MCP servers (0)
  LSP servers (0)

Projected token cost
  Always-on:   ~139 tok   added to every session

Per-component (rounded)
  component                      always-on  on-invoke
  claude-automation-recommender       ~140      ~4.1k
```

ここで分かることが2つあります。ひとつは、**このプラグインの中身はスキル1枚だけ**だということです（`Skills (1)`）。もうひとつは、**常時かかるコストが約139トークンしかない**ことです。常駐する重い仕組みではなく、呼んだときだけ約4.1kトークンを使って働く道具だ、と理解しておけば十分です。

## Step 2：ここで一度つまずきます（罠A）

さて、新しいプロジェクトを始めるところです。フォルダを作って、その中で Claude Code を起動して、さっそく診断させてみます。

```bash
# 実行場所＝ターミナル
mkdir my-first-app
cd my-first-app
claude
```

そしてプロンプトで「Claude Code のセットアップを手伝って」と頼みます。ところが、**返ってくるのは診断レポートではありません。** 実際に空のフォルダで走らせた結果が、これです（原文は英語なので趣旨を訳しています）。

> このディレクトリは完全に空です。コードも `package.json` も git リポジトリもなく、解析するものが何もありません。automation-recommender スキルは、あなたのコードベースが使っているツールやフレームワークを読んで動くので、実際のコードがここに置かれるまでは、推薦の根拠になるものがありません。

**これが罠Aです。空のフォルダでは、このプラグインは空振りします。**

理由は仕組みを見れば当然で、このスキルは `package.json` や `pyproject.toml` といった**マニフェストファイルと、フォルダ構成を読んで判定する**作りになっているからです。判定材料が1つも無ければ、出せる答えも無い、というだけの話です。

つまり「まっさらな状態から、まず設定を整えてもらう」という使い方は**このプラグインの守備範囲ではありません**。順序が逆で、正しくは次のようになります。

**最小でいいので中身を作る → それから診断させる → 出てきたものを置く**

## Step 3：最小の骨組みを作る

そこで、まず「これから何を作るか」が分かる程度の骨組みを置きます。**完成させる必要はありません。** 使う言語とフレームワークが分かるだけの、いちばん薄い状態で十分です。

今回は例として、Next.js と React で作り、データベースに Supabase を使い、整形は Prettier、テストは Vitest を使う、という構成にしました。この時点でのフォルダの中身は次のとおりです。

```
my-first-app/
├── package.json        ← next / react / @supabase/supabase-js / prettier / eslint / vitest
├── tsconfig.json       ← strict: true
├── .prettierrc         ← semi: false
├── src/
│   ├── page.tsx
│   └── components/
│       └── Button.tsx
└── tests/
    └── basic.test.ts
```

中身のコードは1行ずつしかありません。それでも、**この骨組みが「判定材料」として十分に効きます**。次でそれが分かります。

### `package.json` は必須ではありません

ここで誤解しやすい点を先に潰しておきます。上の例に `package.json` が出てくるので「npm のプロジェクトでないと使えないのか」と読めてしまいますが、**そうではありません。**

念のため補足すると、`package.json` は npm（Node.js のパッケージ管理）のプロジェクト定義ファイルで、webpack のようなバンドラの設定ファイルではありません。バンドラの設定は `webpack.config.js` や `vite.config.ts` に書きます。

このスキルが必要としているのは `package.json` そのものではなく、**「これは何をするプロジェクトなのか」が読み取れる材料**です。SKILL.md の Phase 1 が見ているのは、マニフェスト（`package.json` / `pyproject.toml` / `Cargo.toml` / `go.mod` / `pom.xml`）**だけではなく**、フォルダ構成（`src/` `tests/` `components/` など）、ソースの import 文、そして `.claude/` と `CLAUDE.md` の有無です。なんなら「何をするプロジェクトなのか」を説明したテキストファイル1つでも構いません。材料はどれか1種類あればよく、多いほど診断が具体的になります。

| フォルダの中身 | 診断できるか | 何が出るか |
| --- | --- | --- |
| 空フォルダ | **✗ 出ない** | 「解析するものがありません」で終わる |
| コードファイル数個だけ | ○ 出る | import 文と拡張子から言語・フレームワークを推定して判定する |
| `package.json` ＋ ソース | ◎ いちばん具体的 | 依存ライブラリ名まで読めるので、MCP サーバーを名指しできる |
| **説明テキスト1枚（非開発）** | **△ 出るが薄い** | 診断は通るが推薦が一般論に寄る。下記のとおり |

### 開発プロジェクトでなくても使えますが、効き目は条件によります

「そもそもコードを書かないプロジェクトではどうなるのか」を確かめるため、`README.md` を**1枚だけ**置いたフォルダで走らせてみました。中身は「町内会の会計を管理する。プログラムは書かない。レシートの金額を Excel に手入力していて毎月3時間かかる。過去の支出を調べるのに紙の束をめくっている」という説明文です。

結果として、**診断そのものは通りました。** 出力の作りも悪くありません。

> **フック・サブエージェント・lint/format 系の自動化は対象がありません。** これらはファイル編集イベントやコードレビューを前提にするため、コードのないこのプロジェクトでは推奨できるものがありません。無理に設定しても発火しません。

このように、**該当しないカテゴリを自分から外してきます**。そのうえで、README に書かれた困りごとに答えるものを出してきました。レシート画像から日付・金額・費目を抽出して台帳に追記する `receipt-entry` スキル、年度末の収支報告書を作る `year-end-report` スキル、その土台になる `pdf` / `xlsx` スキル、スキャン保管フォルダ用の filesystem MCP、という具合です。

### ただし、素の Claude と比べると差は小さいです

ここで止めれば「非開発でも使えます」という気持ちのよい結論になりますが、**比較していない結論は信用できない**ので、条件を変えてもう一度試しました。プラグインを一時的に無効にして（`claude plugin disable claude-code-setup`、実行場所＝ターミナル）、同じフォルダで素の Claude に同じことを頼んだのです。

結果は、**素の Claude のほうが具体的でした。** フォルダ構成の提案、`CLAUDE.md` の雛形、そのまま貼れるスラッシュコマンド3本の中身、そして「今日やること」3ステップまで出してきました。プラグイン版は「`receipt-entry` スキルを作るとよい」という**一段抽象度の高い提案**で止まっていました。しかも素の Claude は、聞いてもいないのに自分からこう言いました。

> 公式の `claude-code-setup` はプロジェクトを読んで「何を入れるべきか」を提案してくれますが、対象は主に**コードのツール**です。このフォルダのような文書だけのプロジェクトではほぼ何も提案されません。この手のプロジェクトは、`CLAUDE.md` とスラッシュコマンドを手で用意するのが正解です。

理由は SKILL.md を見れば分かります。**Phase 2 の対応表が、すべてコードの信号でできている**からです。「React があれば Playwright MCP」「Prettier があれば整形フック」「認証コードがあれば security-reviewer」といった具合で、非コードのプロジェクトではこの表が1行も引けません。そのとき残るのは「5カテゴリで漏れなく考える」という**枠組みだけ**で、それはプラグイン固有の知識ではありません。

### 効くかどうかを分けるのは「コード」か「`.claude/` の設定」があるか

とはいえ「プログラミング関連でなければ使えない」も言い過ぎです。**反例があります。** この記事の第2部で当てたプロジェクトは、実はコードを書かないプロジェクトで、`package.json` もソースもありません。それでも優れた診断が返り、`Agent type not found` の実バグまで見つかりました。

違いは、そちらには **`.claude/` の設定一式（`settings.json`・rules・skills）と `CLAUDE.md` がある**ことです。Phase 1 は、コードだけでなく**Claude Code の設定そのもの**も判定材料として見ています。整理すると次のようになります。

| フォルダの状態 | 有効性 | 理由 |
| --- | --- | --- |
| コードがある | ◎ 本領 | 対応表が引けるので、ライブラリ名を根拠にした名指しの推薦が出る |
| コードは無いが `.claude/` の設定が育っている | ◎ 有効 | 設定の抜けや、参照の断線を見つけられる（第2部の例） |
| コードも設定も無い純粋な文書フォルダ | △ 薄い | 対応表が1行も引けない。素の Claude に相談したほうが具体的な答えが返る |

したがって**「非開発でも使えます」で終わらせるのは正確ではありません**。文書だけのフォルダなら、プラグインを呼ばずに Claude へ普通に相談したほうが早いです。このプラグインを呼ぶ価値が出るのは、**読ませる材料としてコードか設定がそこにあるとき**です。

## Step 4：診断させる

Claude Code をこのフォルダで起動して、次のどちらかで呼びます。

**(a) 自然な言葉で頼む**（プロンプトに入力）

```
recommend automations for this project
```

日本語でも通ります。「このプロジェクトに向いた自動化を提案して」「Claude Code のセットアップを手伝って」「どんなフックを入れるべき？」でも起動します。スキルの `description` に、そういう頼み方をされたら起動せよ、と書いてあるためです。

**(b) スキル名を直接指定する**（プロンプトに入力）

```
/claude-code-setup:claude-automation-recommender
```

長いですが、これが確実です。**プラグインが持つスキルは必ず `/プラグイン名:スキル名` という名前空間つきになります**。プラグイン同士で名前がぶつかるのを防ぐためです。(a) の自然文が空振りしたときは、こちらで直接叩いてください。

### 実際に返ってきた診断（全文）

先ほどの骨組みに対して、実際に返ってきたものです。**これが読めれば、この記事の目的はほぼ達成です。**

> ## Claude Code Automation Recommendations
>
> ### Codebase Profile
> - **Type**: TypeScript (strict), Node
> - **Framework**: Next.js 15 (App Router) + React 19
> - **Key Libraries**: `@supabase/supabase-js`
> - **Tooling**: Prettier, ESLint 9, Vitest
> - **Claude config**: none yet (no `.claude/`, no `CLAUDE.md`)
>
> ### 🔌 MCP Servers
>
> **Supabase MCP** — `@supabase/supabase-js` に依存しているのにスキーマも型もリポジトリに無い。Supabase MCP を入れると、Claude がテーブルを直接見て、クエリを実行し、型付きクライアントを生成できる（スキーマを推測しなくてよくなる）。
> `claude mcp add supabase -- npx -y @supabase/mcp-server-supabase@latest --project-ref=<ref>`（読み取り専用トークンを使うこと）
>
> **Playwright MCP** — Next.js + React のフロントエンドなのに、描画結果を検証するテストが無い。Playwright MCP なら実ブラウザを動かしてページを確認し、hydration エラーやアクセシビリティ問題を捕まえられる。
> `claude mcp add playwright -- npx -y @playwright/mcp@latest`
>
> ### 🎯 Skills
>
> **`new-component`** — `src/components/` にコンポーネントが1つあるだけで規約が無い。型付き props、RSC とクライアントの境界、テストの同居、といったテンプレートをスキルにしておくと、増えても形が揃う。
> 置き場所：`.claude/skills/new-component/SKILL.md`／呼び出し：ユーザー専用
>
> **`project-conventions`** — `CLAUDE.md` が無い。App Router のレイアウト、`semi: false`、Jest ではなく Vitest、Supabase クライアントの置き場所、といった「言われないと分からない規約」を書いておけば、毎回説明しなくて済む。
> 置き場所：`.claude/skills/project-conventions/SKILL.md`／呼び出し：Claude 専用
>
> ### ⚡ Hooks
>
> **編集時に Prettier で整形** — `.prettierrc`（`semi: false`）があるのに強制する仕組みが無い。自動整形しておけば、Claude の編集があなたの書式と喧嘩しない。
> 置き場所：`.claude/settings.json` の `PostToolUse`（`Edit|Write` にマッチ）
>
> **`.env` の編集をブロック** — Supabase を使うなら、プロジェクトキーの入った `.env.local` は遅かれ早かれ現れる。`PreToolUse` で止めておけば、秘密を誤って書き込む事故を防げる。
> 置き場所：`.claude/settings.json` の `PreToolUse`
>
> ### 🤖 Subagents
>
> **`test-writer`** — `tests/basic.test.ts` が空のひな型のままで、`test` スクリプトは Vitest に繋がっている。ここがいちばん大きな穴。
> 置き場所：`.claude/agents/test-writer.md`
>
> **`ui-reviewer`** — React 中心なのにアクセシビリティの確認がどこにも無い。セマンティック HTML、ARIA、キーボード操作を見る係を分けると、問題が広がる前に捕まる（`Button.tsx` が空の `<button/>` を返している点など）。
> 置き場所：`.claude/agents/ui-reviewer.md`

### この出力の何が良いのか

一般論の解説記事と決定的に違うのは、**すべての推薦に「あなたのプロジェクトのこの部分を見たからこう言っている」という根拠が付いている**ことです。

`.prettierrc` があるから整形フック、`@supabase/supabase-js` があるから Supabase MCP、`tests/` が空のひな型だから `test-writer`、`Button.tsx` が空の `<button/>` を返しているから `ui-reviewer`。**判断の材料がすべて自分のフォルダの中にあるので、納得できるか検証できます。** ここが「初期設定10選」のような記事との違いです。

なお、各カテゴリで**上位1〜2件に絞る**設計になっています。これは意図的なもので、スキルの中に「圧倒しないこと」と明記されています。もっと見たいときは「MCP の候補をもっと」と頼めば、そのカテゴリだけ3〜5件に増やして返してきます。

## Step 5：出てきたものを実際に置く

ここで**もう一度きちんと言っておきます。このプラグインは診断までで、設定はしてくれません。** 出てきたレポートを見て、置くのは自分（あるいは、改めて Claude に頼む）です。

置き場所は、レポートに全部書いてあります。整理すると次のようになります。

| 出てきたもの | 置き場所 | git で共有するか |
| --- | --- | --- |
| Skills | `.claude/skills/<名前>/SKILL.md` | する |
| Subagents | `.claude/agents/<名前>.md` | する |
| Hooks | `.claude/settings.json` の `hooks` | する |
| MCP Servers | `claude mcp add ...`（実行場所＝ターミナル）／チーム共有なら `.mcp.json` | `.mcp.json` は共有する |
| プロジェクトの前提知識 | `CLAUDE.md` | する |

いちばん簡単なのは、**診断が終わった直後に、そのまま Claude に頼むこと**です。レポートの末尾には「実装を手伝ってほしければ言ってください」と書いてあるので、次のように返せば、そのまま作成まで進みます。

```
上のうち、Prettier の整形フックと project-conventions スキルを作って
```

**全部を一度に入れないでください。** 5カテゴリすべてを一気に入れると、どれが効いているのか分からなくなり、不具合が出たときの切り分けもできなくなります。1つ入れて、動きが変わったことを確認して、次を入れる。この順で進めるのが結局いちばん速いです。

# 第2部：すでに動いているプロジェクトの点検に使う

新規導入だけの道具ではありません。**すでに `.claude/` を育てているプロジェクトに当てて、抜けを探す**使い方ができます。むしろ、こちらのほうが効く場面が多いかもしれません。

やることは同じで、既存プロジェクトのフォルダで Claude Code を起動して、同じように呼ぶだけです。

```
/claude-code-setup:claude-automation-recommender
```

### 実際に、設定を育てているプロジェクトに当ててみた

筆者が1年近く設定を積み上げてきたプロジェクト（`.claude/settings.json` に deny 柵、`paths:` で絞った rule が1本、自作スキルが1本、GitHub MCP 接続済み）に当てたところ、**実際に壊れている箇所が見つかりました。**

> 自作スキル `x-claude-trends` は `subagent_type: "knowledge-researcher"` を呼ぶ作りですが、その定義は隣の `multi-hook` プロジェクトにしか無く、ここで実行すると `Agent type not found` で止まります。スキルが宙に浮いているので、まずこの穴を埋めるのが一番効きます。

確認したところ、**そのとおりでした。** `.claude/agents/` の中身は `.DS_Store` だけで空、一方でスキルの本文には確かに `subagent_type: "knowledge-researcher"` と書いてあります。**呼び出す側だけがあって、呼ばれる側が居ない状態**です。自分では気づいていませんでした。

この種の壊れ方は、人間の目では見つけにくいものです。**設定は書いた時点では動いていて、あとから環境が変わって壊れるから**です（この場合は、エージェントを別プロジェクトに置いたまま、スキルだけをこちらへ持ってきた）。参照先が実在するかどうかを機械的に突き合わせる作業は、まさにこういう道具が得意とするところです。

### 既存プロジェクトに当てるときの読み方

新規のときと違って、既存プロジェクトでは**推薦の受け取り方に注意が要ります**。

- **(a) 「無い」と指摘されたものが、本当に必要とは限らない。** そのプロジェクトの性質上わざと入れていないものまで「入っていません」と言ってきます。理由があって入れていないなら、無視して構いません。
- **(b) 既に別の方法で解決している場合がある。** 実際、上のケースでは「Obsidian 連携は別の CLI で実装済みなので、Obsidian MCP を足すと二重化して混乱する」と、こちらの既存構成を読んだうえで**見送りを推奨**してきました。ここまで読めているなら信用してよい、という判断材料になります。
- **(c) 参照の断線（今回の `Agent type not found` のような指摘）は、優先度が高い。** これは好みの問題ではなく、**壊れている**ので、見つかったら直すべきです。

**要するに、「入れろ」という推薦は取捨選択してよく、「壊れている」という指摘は直したほうがよい**、という読み分けになります。

# 第3部：正体と限界

## 正体はスキル1枚

第1部の `claude plugin details` で見たとおり、このプラグインの中身は**スキル1枚**です。実物のファイル構成はこうなっています。

```
claude-code-setup/
├── .claude-plugin/
│   └── plugin.json          ← version 1.0.0 / author: Anthropic
├── skills/
│   └── claude-automation-recommender/
│       ├── SKILL.md         ← 本体（289行）
│       └── references/
│           ├── mcp-servers.md
│           ├── skills-reference.md
│           ├── hooks-patterns.md
│           ├── subagent-templates.md
│           └── plugins-reference.md
├── README.md
└── LICENSE
```

つまり「プラグイン」という皮をかぶっていますが、**やっていることはスキルそのもの**です。プラグインという形をとっている理由は、マーケットプレイス経由で配れてバージョン管理できるからで、機能の中身がプラグイン固有というわけではありません。

中身の作りも素直で、3段階になっています。

1. **Phase 1（解析）**：`package.json`・`pyproject.toml`・`Cargo.toml`・`go.mod`・`pom.xml` があるかを見て、`.claude/` と `CLAUDE.md` の有無を確認し、`src/` `tests/` `components/` などの構成を調べる。
2. **Phase 2（対応づけ）**：見つけた特徴を推薦へ写像する。「React があれば Playwright MCP」「Prettier があれば整形フック」「認証や決済のコードがあれば security-reviewer」といった対応表が、そのまま SKILL.md に書かれています。
3. **Phase 3（レポート）**：カテゴリごとに上位1〜2件を、理由と置き場所つきで出力する。

**ここまで単純です。** 魔法ではなく、「よくある構成と、それに効く設定」の対応表を持った読み手が、あなたのフォルダを見て表を引いている、というだけの仕組みです。

## 罠B：「全部設定まで完了する」は誤りです

X で、このプラグインを紹介する投稿にこう書かれているのを見かけました。

> 全部ステップバイステップで設定まで完了する。

**これは誤りです。** SKILL.md の11行目に、はっきり書いてあります。

> **This skill is read-only.** It analyzes the codebase and outputs recommendations. It does NOT create or modify any files. Users implement the recommendations themselves or ask Claude separately to help build them.
> （このスキルは読み取り専用である。コードベースを解析して推薦を出力する。ファイルの作成も変更も一切行わない。ユーザーが自分で実装するか、Claude に別途頼んで作ってもらう。）

さらに、フロントマターで**渡されているツールが読み取り系だけ**です。

```yaml
---
name: claude-automation-recommender
description: Analyze a codebase and recommend Claude Code automations ...
tools: Read, Glob, Grep, Bash
---
```

`Write` も `Edit` もありません。**指示文でそう書いてあるだけでなく、道具として持っていない**わけです。だから「設定まで完了する」ということは起こりません。

紹介記事を読むときは、こういう部分こそ**一次情報で確かめる価値があります**。マーケットプレイスは GitHub の公開リポジトリなので、誰でも中身を読めます。しかも、Claude Code を使っていれば**手元にクローンが落ちています**ので、次の場所を開けば実物が読めます。

```bash
# 実行場所＝ターミナル
ls ~/.claude/plugins/marketplaces/claude-plugins-official/plugins/
```

## 厳密に言うと、read-only は「指示による自己規制」に近い

ここは細かい話ですが、正確に書いておきます。

上のツール一覧をもう一度見ると、`Bash` が入っています。**Bash が使える以上、理屈のうえでは書き込む余地は残っています**（`echo` でファイルに書けてしまう、という意味です）。つまり「read-only」は、Write と Edit を渡さないという設計と、SKILL.md 本文の明示的な指示によって成り立っているのであって、**権限で完全に封じ込められているわけではありません**。

実用上は、指示が明確なので問題は起きないはずです。ただ「権限で塞がれているから絶対に安全」と理解するのは正確ではなく、**本当に触られたくないものがあるなら、自分の `settings.json` の `permissions.deny` で塞ぐのが本筋**です。これはこのプラグインに限った話ではなく、あらゆるスキルとサブエージェントに共通する考え方です。

## コストの目安

`claude plugin details` が出した数字を、もう一度確認しておきます。

- **常時：約139トークン** — 入れておくだけで毎セッションに乗る分。無視できる大きさです。
- **起動時：約4.1kトークン** — 診断を1回走らせるたびにかかる分。

つまり、**入れっぱなしにしておいても負担はほとんどありません**。使うのは「新しいプロジェクトを始めたとき」と「久しぶりに既存プロジェクトを点検したいとき」くらいで、常用するものではないからです。

# まとめ

`claude-code-setup` は、**「Claude Code に何を設定すべきか」という問いにだけ答える、公式の診断ツール**です。設定そのものはしてくれませんし、空のフォルダでは何も出ません。この2点さえ分かっていれば、期待外れになることはありません。

そして、このプラグインが本当に効くのは「初めての導入」だけではありません。**設定を育ててきたプロジェクトに当てて、参照の断線のような「自分では気づけない壊れ方」を見つける**使い方が、おそらくいちばん価値があります。
